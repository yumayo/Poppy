# ファイル内検索と全文検索

## 実装済み: Ctrl+F

Ctrl+Fは選択中のViewerに検索欄を開き、入力に合わせて本文中の文字列を探します。Enter / F3で次、Shift+Enter / Shift+F3で前へ移動し、端で折り返します。検索欄の↑↓でも移動できます。Escまたは×で閉じ、Tabで本文へ戻ります。Aaは大文字小文字を区別する設定です。区別しない場合の変換対象はASCII英字で、日本語・絵文字などはUTF-8の同じ文字列に一致します。

通常表示では未保存の編集を含むDocumentを検索します。UTF-16ファイルも読み込み時に変換済みの本文を使います。差分では表示される変更前・変更後・コンテキスト行を対象にし、Gitのパッチヘッダーや行頭の差分記号は対象から除きます。WSLから読み込んだファイルも同じ処理で、検索のための通信はありません。

`LiteralPattern`はKMPによる部分文字列照合で、検索語と接頭辞表だけを保持します。`TextSearch`は走査カーソル、一致件数、最初・最後・選択対象の位置だけを保持します。一致数に比例するメモリ確保や本文のコピーはありません。照合の計算量は本文長＋検索語長、補助メモリは検索語長に比例します。ナビゲーションも走査し直すため、一致位置の全件キャッシュとのトレードオフがあります。

Viewerは入力・編集から60 ms後に走査を始め、8 KiBの処理単位で時刻を確認し、約2 msを目安にUIへ処理を返します。検索語・タブ・本文が変われば未完了の走査を置き換えます。編集後の再集計ではカーソルと選択を保持し、古い位置を適用しません。強調表示は画面にある行だけで計算します。単一ファイルは既存の16 MiB上限内なので、この段階では並列化による本文コピー・同期・追加スレッドを導入していません。

検索語はUTF-16で512コード単位までです。正規表現・単語境界・複数行・Unicode全体の大文字小文字変換は未対応です。Ctrl+Shift+Fは未実装です。

## 設計案: Ctrl+Shift+F

コードの文字列・記号・識別子の一部・日本語を探す用途では、最初の構成としてインデックスを作らずにファイルを順次読み、ファイル単位で並列に検索する方式を推奨します。初回から使え、外部編集への索引追従も不要です。毎回対象の本文を読むため、巨大なリポジトリではI/Oが支配的になり、索引方式より遅くなる可能性があります。

| 対象 | 実行場所と保持する情報 |
| --- | --- |
| Windowsの保存済みファイル | Windows側で列挙・読み込み・照合。ワーカーごとの固定バッファと小さい結果バッチを保持 |
| WSLの保存済みファイル | 既存のLinuxヘルパー側で列挙・読み込み・照合。Windowsへは相対パス・行・列・抜粋だけを分割送信 |
| 開いている未保存ファイル | エディター側の本文を検索。ディスク側の同じパスを除外し、同じ結果一覧へ統合 |
| 設定と履歴 | 既存のSQLiteへ必要な情報だけを保存 |

並列数と読み込みキューを有界にします。例えば2〜4ワーカー・各64〜256 KiBの読み込みバッファを出発点にし、実機計測で調整します。上限はプロジェクトごとに掛け算せず、アプリ全体で管理します。CPUが多くても、ストレージやWSLの`/mnt/c`で同時読み込みを増やしすぎると遅くなることがあります。リポジトリ全体の本文をメモリへ載せる必要はありません。

検索条件には世代IDを付け、入力が変わったら列挙・読み込み・照合をキャンセルします。結果は一定件数または一定バイト数ずつUIへ届け、表示件数・抜粋長・結果待ちキューに上限を設けます。上限到達と途中エラーは表示し、見つからなかった結果と区別します。端末・Git・保存が長時間の検索に塞がれないよう、検索ワーカーと既存のI/O処理の枠を分けます。

WSLは既存の要求ID・プロジェクトID・世代付きプロトコルを拡張できます。追加するのは検索要求、結果バッチ、完了・取消し応答、送信待ちの上限です。本文全体をWindowsへ転送してから検索する経路は避けます。実機ではWSL1/2、LinuxファイルシステムとDrvFs、切断時の取消し・再接続を確認します。ファイル内検索に比べて作業は増えますが、既存ヘルパーを利用できるため、別の接続基盤は不要です。

除外設定も性能を左右します。`.git`に加えて`.gitignore`や検索固有の除外、隠しファイル、バイナリ、文字コード、シンボリックリンク、大きいファイルの扱いを明確にします。Ctrl+Pのファイル名一覧は本文を持たず、全件が検索対象として適切とも限らないため、そのまま全文インデックスとして扱いません。

## SQLiteと外部ライブラリの選び方

SQLiteはディスク上のDBで、全件が常にメモリに載るわけではありません。FTS5による永続索引は繰り返し検索を速くできます。一方で、本文・索引の容量、初回構築、外部編集との同期、削除・名前変更の追従が必要です。通常の単語トークナイザーはコードの任意部分一致や日本語の区切りにそのまま適合しません。trigram索引なども候補ですが、短い検索語、検索モード、トークナイザーの条件を確認し、実データで索引サイズと更新負荷を測ってから選びます。現在のビルドはFTS5の有効化を前提にしていません。

単純な部分文字列検索に外部ライブラリは必須ではありません。今回の照合部はWindows/Linuxで共用できます。正規表現・Unicodeの大文字小文字変換・日本語の単語分割まで求める場合は、既存ライブラリの利用価値が上がります。全文検索ではripgrepのような既存エンジンを別プロセスとして使う案もあり、並列走査・除外規則・正規表現を任せられます。その場合はWindows/Linux双方の実行ファイルの同梱と更新、未保存本文との統合、文字コードの対応範囲を決めます。追加依存を採用する際には、組み込み実装と比較してから決定します。

まずストリーミング方式で、初回の結果表示までの時間、全件の検索時間、ピークメモリ、取消しの応答時間を測ります。WindowsとWSLで、それぞれ小規模・大規模リポジトリ、キャッシュがある場合とない場合、結果が極端に多い検索を比較します。索引は、その結果で不足が明らかになった場合の追加候補です。
