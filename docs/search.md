# ファイル内検索と全文検索

## 実装済み: Ctrl+F

Ctrl+Fは選択中のViewerに検索欄を開き、入力に合わせて本文中の文字列を探します。Enter / F3で次、Shift+Enter / Shift+F3で前へ移動し、端で折り返します。検索欄の↑↓でも移動できます。Escまたは×で閉じ、Tabで本文へ戻ります。Aaは大文字小文字を区別する設定です。区別しない場合の変換対象はASCII英字で、日本語・絵文字などはUTF-8の同じ文字列に一致します。

通常表示では未保存の編集を含むDocumentを検索します。UTF-16ファイルも読み込み時に変換済みの本文を使います。差分では表示される変更前・変更後・コンテキスト行を対象にし、Gitのパッチヘッダーや行頭の差分記号は対象から除きます。WSLから読み込んだファイルも同じ処理で、検索のための通信はありません。

`LiteralPattern`はKMPによる部分文字列照合で、検索語と接頭辞表だけを保持します。`TextSearch`は走査カーソル、一致件数、最初・最後・選択対象の位置だけを保持します。一致数に比例するメモリ確保や本文のコピーはありません。照合の計算量は本文長＋検索語長、補助メモリは検索語長に比例します。ナビゲーションも走査し直すため、一致位置の全件キャッシュとのトレードオフがあります。

Viewerは入力・編集から60 ms後に走査を始め、8 KiBの処理単位で時刻を確認し、約2 msを目安にUIへ処理を返します。検索語・タブ・本文が変われば未完了の走査を置き換えます。編集後の再集計ではカーソルと選択を保持し、古い位置を適用しません。強調表示は画面にある行だけで計算します。単一ファイルは既存の16 MiB上限内なので、この段階では並列化による本文コピー・同期・追加スレッドを導入していません。

検索語はUTF-16で512コード単位までです。正規表現・単語境界・複数行・Unicode全体の大文字小文字変換は未対応です。

## 実装済み: Ctrl+Shift+F

選択中のプロジェクトを対象に、検索アイコンまたはCtrl+Shift+FでSEARCHサイドバーを開きます。入力から150 ms後に走査し、結果を順次追加します。クリックまたはEnterで該当ファイルを開き、一致箇所を選択して表示します。↑↓で結果を選び、Tabで検索欄と結果一覧を行き来できます。Aaで大文字小文字の区別、Ignore rulesで除外規則の適用を切り替えます。Refresh / F5でディスクを再走査します。

文字列・記号・識別子の一部・日本語を、全文索引なしで検索します。本文をSQLiteに保存せず、リポジトリ全体をメモリに読み込みません。初回から使え、索引と外部編集の同期も不要です。毎回本文を読むため、巨大なリポジトリではI/Oが支配的になり、永続索引より遅くなる可能性はあります。検索モードと大文字小文字の扱いはCtrl+Fと共通です。

| 対象 | 実行場所と保持する情報 |
| --- | --- |
| Windowsの保存済みファイル | Windows側の専用ワーカーで列挙・読み込み・照合 |
| WSLの保存済みファイル | Linuxヘルパーの検索専用枠で列挙・読み込み・照合。Windowsへは相対パス・行・列・抜粋だけを分割送信 |
| 開いている未保存ファイル | UI側で生のEditBufferを約2 msずつ検索。本文のスナップショットを作らず、ディスク側の同じパスを除外して統合 |
| SQLite | 従来の状態保存のみ。検索語・検索結果・全文索引は保存しない |

既定の並列数は2、読み込みバッファはワーカーごとに64 KiBです。列挙キューは128ファイル、プロセス全体のファイル検索枠は最大4です。プロジェクトやサイドバーを隠すと検索をキャンセルし、非表示のプロジェクトでファイル走査を続けません。プロジェクトごとの調整用スレッドは初回検索時に作成し、走査完了後は待機します。WSL側にも同じ走査エンジンを使います。Linuxヘルパーの検索要求は専用のキューで順に処理し、通常のファイル・Git操作用の3枠を占有しません。

結果は最大2,000件、構造体と文字列の概算で2 MiBが上限です。抜粋は512バイト以内で、一致箇所とその手前を表示します。ワーカー内のファイル単位の結果にも同じ上限を適用します。ファイル末尾まで文字コードを検証してから32件以下のバッチを通知し、後半にNULや不正な文字が見つかったファイルの一致を誤って表示しません。結果は完了順に並びます。UIへの通知をまとめ、受信待ちと表示済みの結果を合わせて同じ件数・容量の予算を使います。上限到達・読み込みエラー・対象外ファイルの件数は検索欄の下に表示します。

入力変更・Esc・プロジェクトやサイドバーの切り替えで検索ジョブを取り消し、古いジョブの結果を適用しません。未保存本文の編集・保存・タブを閉じる操作も検索を更新します。ディスクの外部編集は次の入力・F5で再走査します。結果を開くときに現在の本文と検索語を照合し、一致しなければ再検索を案内します。検索によるファイルの書き換えはありません。

WSLでは要求ID・プロジェクトID・接続世代を既存の長さ付きフレームで検証します。除外する未保存ファイルの相対パスをNUL区切りの本文として送り、改行やバックスラッシュを含むLinuxのファイル名も変換しません。この一覧は最大4 MiBです。結果は共有接続の受信スレッドから有界なUIキューへ直接渡し、接続側に全件の一覧を重ねて保持しません。10分の上限で検索だけをキャンセルし、終了を2秒以内に確認できない場合は従来の切断処理を使います。ヘルパー版は2で、配布済みバイナリのSHA-256を使う既存の更新処理で配置します。

### 対象と除外規則

隠しファイルを含む通常ファイルを検索します。UTF-8（BOMあり・なし）とBOM付きUTF-16 LE/BEに対応し、UTF-16はUTF-8へ小さく分けて変換します。行は1始まり、列はUnicodeの文字単位で1始まり、選択用の位置はデコード後のUTF-8のバイト数です。NUL・不正な文字コード、16 MiB超、100万行超、UTF-8で表せないパスは対象外です。ディレクトリ・ファイルのリンクとWindowsのreparse pointは辿らず、FIFOも開きません。

`.git`・`.hg`・`.svn`はIgnore rulesを無効にしても除きます。有効な場合は各階層の`.gitignore`・`.ignore`と、通常の`.git`ディレクトリ内の`info/exclude`を読みます。`*`・`?`・`[]`・`**`、`!`による打ち消し、ルート基準・ディレクトリ限定・コメント・エスケープを扱います。除外された親ディレクトリは走査しません。Gitのグローバル設定、ユーザーのグローバル除外、worktreeの`.git`ファイルの参照先は読みません。未保存の開いたファイルは明示的に開いた本文として検索し、ディスク用の除外規則を適用しません。

走査の深さは128、ディレクトリ数は10万、相対パスは4,096バイトが上限です。除外規則は1ファイル64 KiB、読み取り量と管理情報の予算は検索全体で1 MiB、最大1万規則、1行512バイトです。上限に達した場合も結果の制限やエラー件数として表示します。Ctrl+Pのファイル名一覧を全文検索用に複製する処理はありません。

### 検証と参考計測

コアテストはUTF-8/UTF-16、日本語・絵文字・CRLF、長い行、後半で見つかるバイナリや不正文字、除外規則、リンク、未保存パスの除外、結果の件数・容量制限、取消し、通信形式を確認します。Linuxヘルパーの結合テストは実パイプで結果・除外・件数制限・取消しと接続の継続を確認します。WindowsのGUIテストには、検索結果からのファイル表示・スクロール・一致範囲の選択と、未保存本文の再検索を追加しています。Windows上でのGUI・IMEとWindows + WSLの組み合わせは実機での検証が必要です。

`dp ctest --test-dir /build/linux -R poppy_content_search_workload -V`で、64ファイル・約16 MiBの合成データを1・2・4並列で走査できます。各ファイルは256 KiBのASCII本文と末尾の一致1件で、検索は大文字小文字を区別しない設定です。ファイル作成直後のLinuxのローカルファイルシステムで測るため、キャッシュがある状態の参考値です。

| 並列数 | 最初の結果 | 全件完了 |
| --- | --- | --- |
| 1 | 2 ms | 99 ms |
| 2 | 1 ms | 50 ms |
| 4 | 1 ms | 27 ms |

この実行のテストプロセス全体のピークRSSは4,116 KiBでした。Windowsアプリ全体のメモリ使用量、WSL・DrvFs、キャッシュがない場合や多数の除外規則があるリポジトリの性能を示すものではありません。既定値はCPU・I/Oの占有を抑えるため2並列にしています。

## SQLiteと外部ライブラリの選び方

SQLiteはディスク上のDBで、全件が常にメモリに載るわけではありません。FTS5による永続索引は繰り返し検索を速くできます。一方で、本文・索引の容量、初回構築、外部編集との同期、削除・名前変更の追従が必要です。通常の単語トークナイザーはコードの任意部分一致や日本語の区切りにそのまま適合しません。trigram索引なども候補ですが、短い検索語、検索モード、トークナイザーの条件を確認し、実データで索引サイズと更新負荷を測ってから選びます。現在のビルドはFTS5の有効化を前提にしていません。

単純な部分文字列検索に外部ライブラリは必須ではありません。今回の照合部はWindows/Linuxで共用できます。正規表現・Unicodeの大文字小文字変換・日本語の単語分割まで求める場合は、既存ライブラリの利用価値が上がります。全文検索ではripgrepのような既存エンジンを別プロセスとして使う案もあり、並列走査・除外規則・正規表現を任せられます。その場合はWindows/Linux双方の実行ファイルの同梱と更新、未保存本文との統合、文字コードの対応範囲を決めます。追加依存を採用する際には、組み込み実装と比較してから決定します。

今後はWindowsとWSLで、小規模・大規模リポジトリ、キャッシュがある場合とない場合、結果が極端に多い検索を比較します。索引は、その結果で不足が明らかになった場合の追加候補です。
