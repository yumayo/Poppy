# 複数プロジェクトの実装メモ

設計元は `.context/multi-project-design.md` v0.3。通常のファイル表示、差分、固定タブ、Git、Ctrl+Pを保持しながら、プロジェクトの追加・切り替え・終了と専用ターミナルを実装した。

## 所有関係

`workspace.cpp` のWorkspaceが一覧・選択・保存ワーカー・AI通知キューを所有し、開いている各項目が `ProjectRuntime` を所有する。`app.cpp` は1プロジェクトのコントローラーで、ツリー、Git結果、タブ、ビューアー、検索インデックス、変更監視、ファイル／Gitワーカーを保持する。各プロジェクトのワーカーは独立しているため、同じ `file` / `git` / `dir:<id>` というキーでも他プロジェクトの要求をまとめない。

初期実装では共有コントロールへモデルを付け替える代わりに、プロジェクトの子ウィンドウとコントロールを保持して表示を切り替える。これにより、ツリーノード・幅キャッシュ・スクロール・本文・検索一覧を再構築しない。非表示中の結果も所有元のコントローラーだけへ反映する。プロジェクト終了時はワーカーを停止し、完了コールバックを破棄してからコントローラーを破棄する。保存と初期読み込みの完了はプロジェクトIDと要求番号から生存対象を引き直す。

各TerminalSessionは保存用ID・名前・起動フォルダー、保持されるTerminal（ConPTY／VTモデル／ビュー）、起動ごとの通知ID、AI状態を所有する。非選択端末のウィンドウも保持し、表示切り替えではプロセスを終了しない。全端末を順番に処理する共通ポンプで、約16 msあたり5 msの処理予算と1回8 KiBの読み取り上限を使う。非表示の端末は最後の有効な画面サイズを保ち、IME位置は更新しない。

プロジェクト切り替え時は、元の表示位置とフォーカスをメモリへ反映し、保持された表示面を表示する。Git再取得と存在確認は表示後に要求する。SQLiteへの保存は650 ms後の保存ワーカーにまとめる。本文は全体64 MiBを目安に、古い非表示プロジェクトから解放する。これは本文・行索引・差分行の容量であり、ツリー・検索一覧・ターミナルを含むアプリ全体の上限ではない。コントロール保持による描画資源とワーカーの増加は実機で計測する。

AI通知は登録済みの通知IDだけを、プロセス内の`AiEventQueue`へ最大1,024件保持する。IDを解除すると配送待ちも除去する。パイプの読み取りスレッドからUIへメッセージを送り、表示を更新する。`activityText`は最大512 Unicode文字で検証し、永続化しない。TCP/HTTP受信サーバーやWinsock依存は持たない。

WSLターミナルの通知は、各TerminalSessionが所有するHookPipeと専用WSLヘルパーで受け取る。CLIやシェルの起動前にUnixソケットを開き、`AICONTAINER_EVENT_SOCKET`を自動設定する。通常の`aicontainer`がソケットだけをコンテナへ渡し、hookからの通知を匿名パイプでPoppyへ返す。通知IDはコンテナへ渡さず、Windows側のセッション所有者で付与して通知キューへ配送する。対話PTY・ファイル操作の接続とは独立し、wslc・起動プロファイル・コンテナからのIP通信は使用しない。標準入力のEOFまたは出力切断でリレーとソケットを終了する。WindowsプロジェクトのPowerShellも、既定WSLに単独の通知ヘルパーをブートストラップし、後から入力される`wsl`へソケットを引き継ぐ。ヘルパーの転送は専用スレッドで行い、開始待ちの期限と終了時のI/O取消しを設ける。WSLを起動できない場合は理由を保持し、PowerShell自体は起動する。

## 検証範囲

LinuxのCTestには、AI状態の遷移・集約・本文検証に加え、通知キューの端末別配送、終了した端末の通知破棄、上限からの復帰、複数スレッドからの配送を含む。Pythonでは導入済みのCodex・Claude hookをUnixソケットへ送信し、設定の導入・解除と、ソケット未設定時には通知しないことを確認する。

Windowsで実行するテストには、A→B→C→AでのノードID・本文・スクロールの保持、非表示プロジェクトの変更反映、シェルの生存、別ターミナルの追加、非選択プロジェクトの終了、再起動時の一覧・端末構成の復元とプロセスの未起動を追加した。読み込み済みのプロジェクトの切り替え時間も出力する。これらのWindowsテストは、このLinux環境では実行していない。

実CLIのhook発火、Windowsの`wsl.exe`とWSLENVによる自動設定、実Dockerのソケットマウントは実機確認が必要。導入方法は [AI連携手順](../integration/ai/README.md) を参照。

HTTP廃止後の検証は既存のCTest 17対象、hookの11テスト、実WSLリレーの11テストと、Windows版のクロスビルドを対象にする。

通知リレーは、ビルド済みのWSLヘルパーと導入済みのCodex・Claude hookをUnixソケットと匿名パイプで検証する。Poppy用変数なしの通知、Unicode、不正データ、件数・バイト数上限、読み取りが遅い場合の復帰、分割送信、端末間の独立性、切断時の後始末、単独ヘルパーの初回配置・再利用・不正な起動モードの拒否を対象にする。ai-container側では通常の`aicontainer`によるソケットの自動マウントと複雑なパスの引用をDockerモックで検証する。

## Windowsでの追加確認

1. `cmake -S . -B out -A x64 -DBUILD_TESTING=ON`、`cmake --build out --config Release`、`ctest --test-dir out -C Release --output-on-failure` を実行する。
2. 5プロジェクトを追加し、それぞれAIとシェルを1つずつ起動する。CodexとClaude Codeを混在させ、応答待ち・実行中・完了の同時表示と、対象端末の確認後もAI状態が残ることを確認する。
3. 非表示の端末で大量出力を続け、別プロジェクトの入力と通知が応答することを確認する。プロジェクト名のクリックと状態アイコンのクリックで移動先が異なることも確認する。
4. 通知ID・状態・受信時刻だけを使って通知遅延を測り、読み込み済み切り替えの最初の描画まで100 ms以内という目標と分けて記録する。初回追加やキャッシュ再読込の完了時間は別にする。
5. `scripts/measure-memory.ps1` をPoppy単体と `-IncludeChildren` の両方で実行する。後者はWindowsの子プロセスの合計であり、Linux側のコンテナのメモリは別に計測する。
6. WSLターミナルで`aicontainer codex`を起動し、通知用の`.aicontainer`設定なしで対象端末へ通知されることを確認する。片方のターミナルの終了時も別端末の通知が継続し、終了した側のソケットだけが削除されることを確認する。

切り替え時間、入力応答、通知遅延、メモリの実測値は未取得。
